# @numeratica/mcp — Engineering Audit

> **Status: all 16 findings resolved in v0.1.3 (2026-07-27).** This document is
> kept as history — the reasoning behind each fix is worth more than the fix. Every
> finding has a test, and each of those tests was verified by mutation: the fix was
> reverted one at a time to confirm the suite actually fails. One of those runs
> found a bug in a *test* (#13's fixture never split a surrogate pair, because a
> 500-unit cut across two-unit emoji lands on a boundary), which is the sort of
> thing this audit's own method was built to catch.

**Date:** 2026-07-25 · **Scope:** `src/bridge.js`, `bin/numeratica-mcp.js`, `test/bridge.test.js`, `package.json`, `tsconfig.json`, `.github/workflows/ci.yml` (v0.1.1, 160 LOC of source)
**Categories:** bugs & correctness, performance, architecture & maintainability

**Method.** Full read of every source file. The concurrency finding (#1) was reproduced empirically against the real `run()` with a mock `fetch`. Protocol claims are checked against the [MCP Streamable HTTP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), quoted inline.

**Framing.** The design goal — "deliberately dumb", forward verbatim, ship no calculation logic — is the right call and the code honours it cleanly. Almost everything below follows from one structural gap: the bridge is written as *a pipe*, but the thing on either end of it is *a protocol with a session, a content-negotiation contract, and concurrent in-flight requests*. A pipe that ignores those three works right up until it doesn't.

---

## Critical & High

### 1. Requests are forwarded strictly one at a time — one slow tool call blocks every other

**Severity: High (performance)** — `src/bridge.js:136`

```js
export async function run(opts) {
  const rl = createInterface({ input: opts.stdin, crlfDelay: Infinity });
  for await (const line of rl) {
    const out = await forward(line, opts);
    if (out !== null) opts.write(out);
  }
}
```

The `await` inside `for await` means line *n+1* is not even read, let alone dispatched, until line *n*'s HTTP round-trip has completed. JSON-RPC explicitly permits multiple in-flight requests distinguished by `id`, and MCP clients use that: a model that emits three tool calls in one assistant turn produces three `tools/call` messages back-to-back.

**Reproduced.** Two requests written to stdin together, upstream latency 300 ms and 10 ms:

```
completion order [id, ms]: [[1,303],[2,314]]
total: 316 ms   (concurrent would be ~300 ms)
```

Request 2 was answerable in 10 ms and took 314 ms. The penalty is unbounded in the slow request's latency: a 40-second `retirement_monte_carlo` delays a 50 ms `tax_bracket_room` behind it by the full 40 seconds.

**Fix.** Dispatch without awaiting, and let the ordering fall out of the ids (which is what ids are for):

```js
export async function run(opts) {
  const rl = createInterface({ input: opts.stdin, crlfDelay: Infinity });
  const inflight = new Set();
  for await (const line of rl) {
    const p = forward(line, opts)
      .then((out) => { if (out !== null) opts.write(out); })
      .finally(() => inflight.delete(p));
    inflight.add(p);
  }
  await Promise.allSettled(inflight);   // drain before resolving on EOF
}
```

Add a concurrency ceiling (a small semaphore, 8–16) so a runaway client can't open unbounded sockets. Note this makes the drain-before-exit fix in #7 mandatory rather than merely prudent.

### 2. No timeout and no abort signal — a single hung connection wedges the bridge permanently

**Severity: High** — `src/bridge.js:84`

```js
res = await opts.fetch(`${opts.baseUrl}/mcp`, {
  method: 'POST',
  headers: { /* ... */ },
  body,
});
```

No `signal`, no `AbortController`, and Node's `fetch` has no default request timeout — a connection that opens and then goes silent (dropped SYN-ACK after a network change, a load balancer holding the socket, a server that never finishes the response body) hangs for the OS TCP timeout, which is on the order of minutes.

**Failure scenario.** Laptop sleeps mid-`tools/call`, or the user's VPN drops. The `await` at line 84 never settles. Because of #1 the `for await` loop is parked on that same `await`, so **every subsequent request is never even read from stdin**. The MCP client sees a process that is alive, holding stdin open, and answering nothing — the worst possible failure shape, because no client heuristic detects it. There is no recovery short of the user killing the process.

**Fix.** Bound every request, and surface the timeout as a JSON-RPC error so the model gets a usable message:

```js
const ac = new AbortController();
const t = setTimeout(() => ac.abort(), opts.timeoutMs ?? 120_000);
try {
  res = await opts.fetch(url, { ..., signal: ac.signal });
} finally {
  clearTimeout(t);
}
```

`err.name === 'AbortError'` should map to a distinct message ("timed out after Ns") rather than being folded into the generic transport error. Make the timeout configurable via `NUMERATICA_TIMEOUT_MS` — a 60-year Monte Carlo legitimately takes longer than a bracket lookup.

### 3. The `Accept` header violates the Streamable HTTP spec — the bridge only works against a lenient server

**Severity: High (interop)** — `src/bridge.js:89`

```js
headers: {
  Authorization: `Bearer ${opts.apiKey}`,
  'Content-Type': 'application/json',
  Accept: 'application/json',
},
```

The specification is unambiguous:

> The client **MUST** include an `Accept` header, listing both `application/json` and `text/event-stream` as supported content types.

A spec-compliant Streamable HTTP server is entitled to reject this request with **406 Not Acceptable**, and real servers do — this is the same defect filed against the Claude Agent SDK ([anthropics/claude-agent-sdk-typescript#202](https://github.com/anthropics/claude-agent-sdk-typescript/issues/202)) and the M365 agents toolkit ([OfficeDev/microsoft-365-agents-toolkit#15421](https://github.com/OfficeDev/microsoft-365-agents-toolkit/issues/15421)).

**Failure scenario.** Today this is latent: `api.numeratica.com` is your own server and evidently accepts it. It becomes live the moment the hosted endpoint is put behind a standards-compliant MCP gateway, migrated to a framework that enforces the check (FastMCP and the official SDKs both do), or a user points `NUMERATICA_BASE_URL` at a self-hosted/proxied deployment. Every request then returns 406 and the bridge relays `Numeratica API error (HTTP 406)` for every single tool call — a total outage whose cause is one missing header.

**Fix.** `Accept: 'application/json, text/event-stream'`. This is a one-line change and it is a prerequisite for #6.

### 4. `MCP-Session-Id` is never captured or echoed — a stateful server breaks after `initialize`

**Severity: High** — `src/bridge.js:84-119`

`forward` reads `res.status` and `res.text()` and nothing else. No response header is inspected, and no state is carried between calls. The spec:

> A server using the Streamable HTTP transport **MAY** assign a session ID at initialization time, by including it in an `MCP-Session-Id` header on the HTTP response containing the `InitializeResult`. If an `MCP-Session-Id` is returned by the server during initialization, clients **MUST** include it in the `MCP-Session-Id` header on all of their subsequent HTTP requests. Servers that require a session ID **SHOULD** respond to requests without an `MCP-Session-Id` header (other than initialization) with HTTP 400 Bad Request.

**Failure scenario.** The hosted endpoint adds session state — per-conversation scenario caching, rate accounting, anything that needs to correlate calls. `initialize` succeeds and returns a session id; the bridge discards it; `notifications/initialized` and every `tools/list` and `tools/call` afterwards arrives with no session header and gets a 400. The user sees the tools appear in Claude Desktop and then fail on every invocation. The bridge's self-description — "it knows nothing about the tool catalog … the bridge auto-syncs with the API" — is what makes this dangerous: the stated design promise is that the server can evolve freely, and this is one of the two ways it can't (the other is #5).

**Fix.** Hold the session id in `run`'s closure and thread it through `forward`:

```js
export async function run(opts) {
  const session = { id: undefined };
  // ...forward(line, { ...opts, session })
}
// in forward, when building headers:
...(opts.session?.id ? { 'MCP-Session-Id': opts.session.id } : {}),
// after a successful fetch:
const sid = res.headers?.get?.('mcp-session-id');
if (sid) opts.session.id = sid;
```

Also handle the spec's recovery path: a **404** on a request that carried a session id means the session expired and the client **MUST** re-initialize — at minimum, clear the stored id so the next `initialize` starts clean.

### 5. `MCP-Protocol-Version` is never sent — the server is forced to assume `2025-03-26`

**Severity: Medium** — `src/bridge.js:86`

> If using HTTP, the client **MUST** include the `MCP-Protocol-Version: <protocol-version>` HTTP header on all subsequent requests to the MCP server. […] For backwards compatibility, if the server does *not* receive an `MCP-Protocol-Version` header […] the server **SHOULD** assume protocol version `2025-03-26`.

**Failure scenario.** A client negotiates `2025-11-25` with the bridge's upstream; the upstream never learns that, so it must serve every request as if it were talking to a `2025-03-26` client — the version whose semantics include JSON-RPC batching and a different tool-result shape. Any version-conditional behaviour the server grows will be wrong for every user of this bridge, permanently and silently.

**Fix.** Capture `protocolVersion` from the `initialize` *result* (the bridge already parses the request body to find the id; parsing the response for this one field is the same class of peek) and set the header on every later request. Falling back to a hard-coded recent version is strictly better than sending nothing.

### 6. An SSE response body is emitted to stdout as a corrupt JSON-RPC frame

**Severity: Medium-High** — `src/bridge.js:114-118`

```js
try {
  return JSON.stringify(JSON.parse(text));
} catch {
  return oneLine(text);
}
```

The spec makes SSE the server's option on any request, not an opt-in:

> If the input is a JSON-RPC *request*, the server **MUST** either return `Content-Type: text/event-stream`, to initiate an SSE stream, or `Content-Type: application/json`, to return one JSON object. The client **MUST** support both these cases.

The bridge never reads `Content-Type`. An SSE body — `event: message\ndata: {"jsonrpc":"2.0","id":1,...}\n\n` — fails `JSON.parse`, so `oneLine` collapses it to `event: message data: {"jsonrpc":"2.0","id":1,...}` and writes *that* to stdout.

**Failure scenario.** The hosted endpoint starts streaming progress notifications for long calculations (the obvious reason to want SSE, and `retirement_monte_carlo` is exactly the shape that wants it). Every long tool call now emits a line that is not a JSON-RPC message. The client's stdio reader either errors on the frame or drops it; the request never resolves. Note the failure is *silent on the bridge side* — `oneLine`'s fallback was written to guarantee single-line output, and it does, which is why this looks like it works.

**Fix.** Branch on the response content type. For `text/event-stream`, parse the frames and write each `data:` payload as its own stdout line (that is precisely the stdio↔HTTP translation this bridge exists to do); for anything else keep the current path. Reserve `oneLine` for genuinely unparseable bodies, where it belongs.

## Medium

### 7. `process.exit(0)` can truncate buffered stdout

**Severity: Medium** — `src/bridge.js:158` (and `:148`)

```js
await run({ /* ... */ });
process.exit(0);
```

`process.stdout` is asynchronous when it is a pipe — which it always is under an MCP client. `process.exit()` does not flush pending writes; it tears the process down. When the last response is large enough to exceed the pipe buffer, the tail is lost.

**Failure scenario.** The final `tools/call` of a session returns a large result (a full Monte Carlo percentile table). `run` resolves on stdin EOF, `process.exit(0)` fires while the write is still draining, and the client gets a truncated frame — or nothing — for a call the server answered correctly. Intermittent and load-dependent, so it reads as a flaky server rather than a bug here. This becomes materially more likely with #1 fixed, since several responses may be in flight at EOF.

**Fix.** Set the code and let the event loop drain naturally:

```js
process.exitCode = 0;   // instead of process.exit(0)
```

For the misconfiguration path at `:148`, `process.exitCode = 1; return;` is equivalent and safe (the existing `return` after `process.exit(1)` shows the intent was already there). The `spawnSync`-based test at `test/bridge.test.js:96` passes either way.

### 8. No retry on transient upstream failures — a single 429 or 503 surfaces as a hard tool error

**Severity: Medium** — `src/bridge.js:104`

```js
if (!res.ok) {
  if (isNotification) return null;
  const detail = text ? `: ${oneLine(text).slice(0, 500)}` : '';
  return jsonRpcError(id, -32000, `Numeratica API error (HTTP ${res.status})${detail}`);
}
```

Every non-2xx is terminal. `Retry-After` is ignored even though 429 is the one status where the server has told you exactly what to do.

**Failure scenario.** A free-tier user hits the rate limit mid-conversation, or the API rolls a deploy and one request lands on a draining instance (503). The model receives `Numeratica API error (HTTP 429)`, and models respond to tool errors by apologising, guessing, or abandoning the task — a retried request 800 ms later would have succeeded. Given the bridge's whole value proposition is "the interesting part is the API; this is just the wire", a wire that doesn't survive a single blip undersells it.

**Fix.** Retry idempotent requests on 429/502/503/504 with exponential backoff (2–3 attempts), honouring `Retry-After` when present. Keep 4xx-other terminal. This composes with #2: the total retry budget must stay inside the request timeout.

### 9. stdout backpressure is ignored

**Severity: Medium** — `src/bridge.js:153`

```js
write: (s) => process.stdout.write(s.endsWith('\n') ? s : s + '\n'),
```

The boolean return of `write` is discarded. When it returns `false` the kernel buffer is full and the correct behaviour is to wait for `'drain'`; instead Node queues the chunk in memory. With #1 in place the serial loop incidentally rate-limits this, but once requests are concurrent a slow-reading client plus several large results is unbounded memory growth in the bridge.

**Fix.** Make `write` return the boolean and have the caller await drain, or wrap stdout in a small async queue:

```js
async function write(s) {
  const line = s.endsWith('\n') ? s : s + '\n';
  if (!process.stdout.write(line)) {
    await new Promise((r) => process.stdout.once('drain', r));
  }
}
```

### 10. `--key` puts the API key in the process table

**Severity: Medium (security)** — `src/bridge.js:27`, `README.md`

```js
const i = argv.indexOf('--key');
if (i !== -1 && argv[i + 1]) apiKey = argv[i + 1];
```

The README presents this as an equal alternative — *"You can also pass the key with `--key <value>` instead of the env var"* — with no caveat. A key on the command line is visible to `ps` for every user on the machine, is captured by shell history when run manually, and is recorded verbatim in MCP client config files that users routinely paste into issue reports.

This sits oddly beside the care taken elsewhere: `validateConfig`'s doc comment specifically notes that its message "never contains the key", and the README states the key "is never logged". Both true — and then the flag hands it to `argv`.

**Fix.** Keep the flag (it is genuinely useful for testing) but document the tradeoff in one line, and prefer `NUMERATICA_API_KEY` in every example. If you want to go further, accept `--key-file <path>` as the recommended non-env option.

### 11. `--key=value` is silently ignored

**Severity: Low-Medium** — `src/bridge.js:27`

`indexOf('--key')` matches only the space-separated form. `--key=nmr_sk_...` — the form roughly half of all CLI users will try first, and the form GNU conventions lead them to — does not match, so `apiKey` falls back to the environment. With no env var set, the user gets `NUMERATICA_API_KEY is required` **while looking at a command line that plainly contains their key**. That is a genuinely confusing five minutes.

**Fix.**

```js
for (const a of argv) {
  if (a.startsWith('--key=')) apiKey = a.slice('--key='.length);
}
const i = argv.indexOf('--key');
if (i !== -1 && argv[i + 1]) apiKey = argv[i + 1];
```

Consider also rejecting unknown `--flags` with a clear message rather than ignoring them.

### 12. The session is never terminated on shutdown

**Severity: Low-Medium** — `src/bridge.js:151-158`

> Clients that no longer need a particular session […] **SHOULD** send an HTTP DELETE to the MCP endpoint with the `MCP-Session-Id` header, to explicitly terminate the session.

`run` resolves on EOF and the process exits. Nothing tells the server the conversation is over, so server-side session state lives until it times out. With `npx` launching a fresh bridge per client restart, a user who restarts Claude Desktop a dozen times a day leaves a dozen orphaned sessions.

**Fix.** After `run` resolves (and on `SIGINT`/`SIGTERM`), if a session id was captured, `fetch(url, { method: 'DELETE', headers: { 'MCP-Session-Id': id, ... } })` with a short timeout, ignoring failures and a 405. Depends on #4.

## Low

### 13. `.slice(0, 500)` on an error body can split a surrogate pair

**Severity: Low** — `src/bridge.js:106`

`oneLine(text).slice(0, 500)` slices by UTF-16 code unit. If the 500th unit lands between the halves of a surrogate pair — plausible when an upstream error echoes user input containing an emoji or an astral-plane character — the result contains a lone surrogate, which `JSON.stringify` emits as an unpaired `\uD83D` escape. Strict JSON parsers reject that; lenient ones produce U+FFFD.

**Fix.** Slice on code points: `[...s].slice(0, 500).join('')`, or use `s.slice(0, 500).replace(/[\uD800-\uDFFF]$/, '')`.

### 14. JSON-RPC batch arrays are handled by accident rather than on purpose

**Severity: Low** — `src/bridge.js:74`

```js
if (msg && typeof msg === 'object' && !Array.isArray(msg)) {
```

An array body leaves `id = null` and `isNotification = false`, so a batch that fails upstream returns a single error with a null id. As it happens **this is now correct** — the current spec requires the POST body to be "a single JSON-RPC *request*, *notification*, or *response*", and batching was removed in `2025-06-18` — so no change in behaviour is needed. But it reads as an oversight, and a `2025-03-26` client is entitled to send a batch.

**Fix.** Make the intent explicit: reject an array body with `-32600 Invalid Request: JSON-RPC batching is not supported`, and say why in a comment. That converts a silent oddity into a diagnosable error.

### 15. `{"id": null}` is treated as a request

**Severity: Low** — `src/bridge.js:75-76`

`isNotification = msg.id === undefined` is the right test, so an explicit `"id": null` is classified as a request and gets an error response echoing `id: null`. Harmless, and arguably the most useful behaviour; noted only because the two lines invite a "fix" that would break notification handling. Worth a one-line comment pinning the distinction.

### 16. Test and CI gaps concentrated exactly where the findings are

**Severity: Low (test coverage)** — `test/bridge.test.js`, `.github/workflows/ci.yml`

The eight existing tests are well chosen — the verbatim-forwarding assertion, the pretty-print compaction case with its explanatory comment, and the `spawnSync` check that a misconfigured bin writes nothing to stdout are all exactly right, and the last one encodes a real stdio-protocol invariant. What is untested is the entire surface above:

- no test asserts two requests can be in flight at once (#1);
- no test for a `fetch` that never resolves (#2);
- no assertion on the `Accept` header, though `seenInit.headers` is already captured and three sibling headers *are* asserted (#3) — this is a one-line addition to an existing test;
- no `MCP-Session-Id` round-trip (#4), no `MCP-Protocol-Version` (#5);
- `mockResponse` has no `headers`, which is *why* #4 and #5 are invisible to the suite;
- no `text/event-stream` body (#6), no 204 path, no non-JSON body reaching `oneLine`.

CI runs a single Node version (20) while `package.json` declares `"node": ">=18"`. Node 18 reached end-of-life in April 2025, so the floor is claiming support for an unmaintained runtime that is never exercised. There is also no `prepublishOnly` script, so `npm publish` can ship a tree that fails `typecheck`.

**Fix.** Add `headers: new Headers(...)` to `mockResponse` and the six assertions above; matrix CI over the versions you actually support (raise the floor to 20 and test 20/22/24); add `"prepublishOnly": "npm run typecheck && npm test"`.

## What's solid

- **The core design decision is right and consistently executed.** Forwarding the body verbatim rather than re-serializing it means the bridge cannot corrupt a request, cannot lag the tool catalog, and cannot leak calculation logic — and the code genuinely does not parse the body for anything except the id. The comment at the top of the file states the invariant and the code keeps it.
- **The single-line stdout framing invariant is understood and defended in depth.** `JSON.stringify(JSON.parse(text))` to normalize a pretty-printed upstream body, `oneLine` as a fallback so an unparseable body still can't emit a multi-line frame, and `write` appending a newline only when absent. The stdio spec's "**MUST NOT** contain embedded newlines" is the subtlest requirement in the transport and it is the one thing here that is airtight — including a test that asserts it with the reasoning written out.
- **Notification handling is correct on all four paths.** `isNotification` is derived from `id === undefined` (not from truthiness, which would misclassify `id: 0`), and it correctly suppresses output on transport error, on non-2xx, on 202/204, and on an empty body. The 202-with-no-body case matches the spec exactly.
- **Credential hygiene in the code is careful.** The key appears only in the `Authorization` header; `validateConfig`'s message is explicitly designed not to contain it; nothing is logged to stdout at all, and the only stderr write is a fixed string. Finding #10 is about the README and the flag, not about the code leaking.
- **Zero runtime dependencies, and `checkJs: true` with `strict: true`** — type-checking JSDoc'd JavaScript gets most of the safety of TypeScript with none of the build step, which for a 160-line `npx`-launched shim is the correct engineering trade. The JSDoc is accurate where it exists.
- **The error shape is right.** `jsonRpcError` echoes the request id so the client can correlate, uses the reserved-for-implementation `-32000`, and bounds the upstream detail rather than relaying an unbounded body.

## Suggested priority order

1. **#3** — one line (`Accept: 'application/json, text/event-stream'`), and it is the difference between "spec-compliant client" and "works only against our own lenient server". Add the missing header assertion to the existing test in the same commit.
2. **#2** — an `AbortController` and a timeout. This is the only finding whose failure mode is a permanently wedged process with no diagnostic, and it is ~10 lines.
3. **#7** — `process.exitCode = 0`. One line, and it must land before #1 makes concurrent in-flight responses at EOF the normal case.
4. **#1** — concurrent dispatch with a semaphore and an EOF drain. The largest user-visible win: multi-tool turns stop serializing. Do it after #7.
5. **#4 + #5** — session id and protocol version. Together they are one change ("carry per-session state through `forward`") and together they are what lets the hosted API evolve without breaking every installed copy of this package. #4 also needs the 404 re-initialize path.
6. **#6** — SSE body handling. Depends on #3 being in place first; unlocks streaming progress on long calculations.
7. **#8 + #9** — retry with backoff, and backpressure. Both are robustness-under-load; #9 matters more once #1 lands.
8. **#16** — the test additions. Worth doing alongside each fix above rather than as a separate pass, since `mockResponse` needs `headers` before #4/#5 are testable at all.
9. **#10 + #11 + #12** — the CLI and lifecycle papercuts. Small, independent, user-facing.
10. **#13 + #14 + #15** — cleanups; batch them.

**Architecture note.** There is no god-file, no duplication, and no leaky abstraction to unwind here — at 160 lines the structure is fine and should stay flat. The one structural change worth making is introducing an explicit per-session state object threaded through `forward` (needed by #4, #5, and #12). Once that exists, `forward`'s signature stops being "here are two strings" and starts being "here is a session", which is an honest description of what a Streamable HTTP client is — and it is the seam every remaining protocol requirement hangs off.
